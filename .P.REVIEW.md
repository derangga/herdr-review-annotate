# Prompt: review the herdr-review research

You are a skeptical senior reviewer. Review `RESEARCH.md` in this directory. It is a research and design
document for `herdr-review`, a native Rust Herdr plugin for code review. Your job is to find what is
wrong, missing, unverified, or over-built, before anyone writes code. Do not write code. Do not edit
`RESEARCH.md`.

## Context

The goal: the user reviews a diff in a TUI and adds comments. The agent can read and add comments on
the same review. One keypress sends the user's comments to the agent, so the user never has to type
"check my comment in hunk". Either side can resolve any comment.

Inputs, all in this directory:

| Path | What it is |
|---|---|
| `RESEARCH.md` | The document under review |
| `hunk/` | Reference: TypeScript diff viewer with an agent CLI and daemon. Start at `AGENTS.md`, `docs/agent-workflows.md`, `packages/hunk/skills/hunk-review/SKILL.md`, `packages/hunk/src/core/review/types.ts` |
| `zeron/` | Reference: Rust gpui desktop app. Start at `crates/ui/src/comments.rs`, `ARCHITECTURE.md` |
| `herdr-annotate/` | Reference: Rust Herdr plugin to copy from. Start at `rust/src/agent_delivery.rs`, `rust/src/store.rs`, `rust/src/herdr.rs`, `herdr-plugin.toml`, `skills/plannotator-tui/SKILL.md` |

Herdr itself is installed (`herdr --version` is 0.9.1). The document also cites the Herdr 0.9.3 docs:
`https://raw.githubusercontent.com/herdrdev/herdr/v0.9.3/docs/next/website/src/content/docs/plugins.mdx`
and the same path with `socket-api.mdx`. Fetch them when you need to check a claim.

## Decisions are fixed

Section 9 of `RESEARCH.md` lists 16 decisions the user already made. Do not reopen them because you
would have chosen differently. Report on a decision only if it is infeasible, internally contradictory,
or contradicts a verified fact. Say which decision and why.

## What to check

Work through these in order. For every claim you check, say whether it is confirmed, wrong, or
unverifiable, with evidence (a file and line, a command and its output, or a doc URL).

### 1. Factual claims about the reference code

- `herdr-annotate/rust/src/agent_delivery.rs`: does it do what sections 2.3 and 4.6 say (readiness
  check, `blocked` and `launch_pending` refusals, ESC stripping, send versus paste)? Is it reusable
  "almost as is", or does it depend on annotation types?
- `hunk`: are the claims in section 2.1 right (daemon with signed sessions, note fields, agents cannot
  create or edit user notes but can remove them, `comment apply --stdin`)?
- `zeron/crates/ui/src/comments.rs`: is the prompt block format and the `cite_path` rename handling
  described correctly?
- Sizes and behaviours stated as fact: "no async runtime", `notify` crate behaviour, `similar` crate
  size, syntect memory. Flag anything stated without a source.

### 2. Claims about Herdr

Run the installed CLI where you can (`herdr plugin pane open --help`, `herdr agent --help`,
`herdr plugin --help`, `herdr pane --help`). Do not run commands that change state, start agents,
close panes, or stop the server.

- Placement and direction: does `plugin pane open` accept `--placement split --direction right
  --target-pane` on 0.9.1, and does it accept `--env`? The document says popup is not available on
  0.9.1. Is that accurate?
- `[[startup]]` hooks: when do they run, do they run under `plugin link`, and does the plan in
  sections 4.7 and 4.8 (a `binary-path` file under `herdr plugin config-dir`) work? Is
  `herdr plugin config-dir` usable for a plugin the agent did not launch?
- Action context: a `review.send` keybinding runs with the focused pane as context. If the focused
  pane is the review pane or a shell, how does `send` find the agent? Does the target resolution order
  in section 4.6 actually work from a keybinding action versus the TUI `S` key?
- `REVIEW_DELIVER_TO` and `--env`: confirm the env variable reaches the pane process, and that the
  pane does not need `HERDR_PANE_ID`.
- `herdr agent prompt` on a `working` agent: what does Herdr actually do? Is "Claude Code queues the
  message" documented anywhere, or is it an assumption?
- Anything in section 3 that is out of date or taken from docs for a version newer than the installed
  one.

### 3. Design soundness

Look for real problems, not style:

- Storage: append-only JSONL with `flock`, a TUI and an agent CLI writing at once. Are appends atomic
  enough? How is event order decided across writers (clock, sequence number)? Can the fold produce
  different states for different readers? What happens on a torn write or a crashed writer holding the
  lock?
- Watching: does the `notify` crate give reliable events for one file appended by another process on
  macOS and Linux? What about the state directory being replaced?
- Anchors: hashing "the line plus context" for drift. Does it survive the common case, an agent
  fixing the exact lines the comment was about? Is "never auto-resolve, tag outdated" workable when
  every fix makes the comment outdated? Does the user end up with a screen full of outdated tags?
- Sent semantics: marking comments `sent` after Herdr accepts the prompt. What if the prompt was
  accepted but the agent never acted (queued behind a long turn, the user cancelled it, the agent was
  restarted)? Is there a way to resend, and is it in the design?
- Resolve model: either side resolves instantly. Can an agent resolve a comment it did not fix? What
  stops a loop where the agent resolves, the user reopens, the agent resolves? Is the `new` marker
  enough?
- IDs: short ids like `u-7f3a`. Collision handling, and what the agent does with a wrong id.
- Security: agent-authored comment text rendered in the user's terminal (control sequences), user
  comment text pasted into an agent prompt (prompt injection from file contents or from other
  comments), the absolute binary path inserted into a prompt, the `outbox` file written to a
  predictable path.
- Git: untracked files, binary files, submodules, huge diffs, CRLF, renames with edits, files deleted
  then recreated, a dirty worktree changing while the user reviews, `base...HEAD` when the base is
  missing or equals HEAD. Does the diff pipeline in section 4.3 cover them?
- Worktrees: reviews are keyed by repo root, so two Herdr worktrees of one repo are two reviews. Is
  that consistent with how Herdr names workspaces, and with target agent resolution?
- Memory and speed: are the budgets in section 5 plausible, and is anything in the design likely to
  break them (loading all comments, re-parsing the whole diff on every file event, rendering)? Is
  "hunk uses much more memory" supported by anything? The document admits it did not measure.

### 4. Over-building

Apply "the best code is the code never written". List what can be cut or deferred from v1 without
losing the core loop (comment, send, agent replies and resolves, user sees it). Candidates to look at:
file-level comments, ranges, `seen` events, archive, outbox file, startup hook, paste mode, two diff
specs, quit prompt, the `skill` and `startup` subcommands. For each, say keep or cut and why. Do not cut
anything that is a fixed decision unless it is infeasible.

### 5. Document quality

- Contradictions between sections, between the text and the Mermaid diagrams, and between the manifest
  sketch and the subcommand table.
- Missing pieces a builder would hit in the first week: error handling, config file, logging,
  tests, CI, release and install flow.
- Claims phrased as certain that are really assumptions. The document marks some; find the ones it
  missed.
- Whether each milestone has a check that tells you it is done.

## Rules

- Verify before you claim. If you cannot verify something, say "unverified", not "wrong".
- Quote or cite evidence. Prefer `path:line` for files and the exact command for Herdr behaviour.
- Do not invent Herdr features. If a feature is not in the installed CLI or the docs, say so.
- Rank by consequence: a wrong fact that would break the build outranks a wording problem.
- Keep it short. No praise, no summary of what the document says.
- Do not modify any file in `hunk/`, `zeron/`, `herdr-annotate/` or `RESEARCH.md`.
